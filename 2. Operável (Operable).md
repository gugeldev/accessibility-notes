
O princípio operável possui cinco diretrizes:

| Diretriz | Nome                               | Objetivo                       |
| -------- | ---------------------------------- | ------------------------------ |
| 2.1      | Keyboard Accessible                | Acessível por teclado          |
| 2.2      | Enough Time                        | Tempo suficiente               |
| 2.3      | Seizures and Physical Reactions    | Convulsões e reações físicas   |
| 2.4      | Navigable                          | Navegável                      |
| 2.5      | Input Modalities                   | Modalidades de entrada         |
## 2.1 Acessível por teclado

Essa diretriz garante que todas as funcionalidades de uma interface possam ser utilizadas por meio de um teclado, sem exigir o uso de mouse ou outro dispositivo 'apontador'.

A ideia é permitir que pessoas com limitações motoras ou que utilizam tecnologias assistivas consigam navegar e interagir com a aplicação. 

Exemplos de acessibilidade nessa diretriz:

- Permitir navegação entre elementos utilizando `Tab` e `Shift` + `Tab`.
- Permitir acionar botões utilizando `Enter` ou `Space`.
- Permitir navegar por menus, formulários e diálogos sem utilizar o mouse.
- Garantir que componentes personalizados também ofereçam interação por teclado.

Exemplo de implementação de um botão acessível: 

```html
<button type="button"> 
	Enviar formulário
</button>
```

Elementos nativos como `button` e `a` (com `href`) já oferecem suporte à interação por teclado, além da semântica adequada. 

### Critérios de sucesso

#### 2.1.1 Keyboard (Nível A)

Todas as funcionalidades precisam ser acessíveis por teclado, exemplos:

- Botões precisam poder ser acionados pelo teclado.
- Menus e formulários precisam permitir navegação sem mouse.
- Componentes personalizados precisam oferecer interação por teclado.

Exceção: funcionalidades que dependem da trajetória do movimento do usuário, e não apenas dos pontos de início e fim, como desenhar à mão livre.

#### 2.1.2 No Keyboard Trap (Nível A)

O usuário não pode ficar preso em um elemento ou componente ao navegar utilizando o teclado, exemplos:

- Deve ser possível sair de campos e componentes utilizando o teclado.
- Modais precisam permitir que o usuário saia deles por meio de uma interação acessível.
- Componentes que controlam o foco precisam permitir sua saída.

Se sair do componente exigir algo além de `Tab`, setas ou `Esc`, o usuário precisa ser informado de como sair.

Manter o foco dentro de um modal aberto não viola o critério (é inclusive recomendado), desde que seja possível fechá-lo, normalmente com `Esc`.

#### 2.1.4 Character Key Shortcuts (Nível A)

Atalhos que utilizam apenas uma tecla de caractere (letras, números ou símbolos) precisam oferecer formas de evitar acionamentos acidentais, exemplos:

- Permitir desativar o atalho.
- Permitir configurar o atalho para utilizar uma combinação de teclas, como `Ctrl + K`.
- Ativar o atalho somente quando determinado componente estiver em foco.

## 2.2 Tempo suficiente

Essa diretriz trata do tempo disponível para que os usuários consigam ler, compreender e interagir com o conteúdo. 

A ideia é garantir que pessoas com diferentes necessidades tenham tempo suficiente para realizar ações, sem perder informações ou funcionalidades por causa de limites de tempo. 

Exemplos de acessibilidade nessa diretriz:

- Permitir que o usuário estenda o tempo de uma sessão antes de expirar.
- Avisar antes de encerrar uma sessão por inatividade.
- Permitir pausar, interromper ou ocultar conteúdos que se movimentam automaticamente.
- Evitar atualizações automáticas que interrompam a leitura.
- Oferecer controles para conteúdos animados ou temporizados.

Exemplo de implementação com aviso de expiração de sessão: 

```js
function warnBeforeExpiration() {
  const shouldExtend = confirm(
    "Sua sessão está prestes a expirar. Deseja continuar?"
  );

  if (shouldExtend) extendSession();
}
```

O aviso precisa aparecer com pelo menos 20 segundos de antecedência, para que o usuário tenha tempo de responder.

### Critérios de sucesso

#### 2.2.1 Timing Adjustable (Nível A)

Quando existe um limite de tempo definido pelo conteúdo, o usuário precisa conseguir desativá-lo, ajustá-lo ou estendê-lo, exemplos:

- Permitir estender o tempo de uma sessão antes de sua expiração.
- Oferecer a possibilidade de desativar limites de tempo quando não forem essenciais.
- Permitir aumentar o tempo disponível para preencher formulários ou realizar atividades.

Regras para cada opção:

- Desativar: o usuário pode desligar o limite antes de ele começar.
- Ajustar: o usuário pode aumentar o limite para pelo menos 10 vezes o tempo padrão.
- Estender: o usuário é avisado antes de expirar, tem pelo menos 20 segundos para estender com uma ação simples (como apertar uma tecla) e pode estender pelo menos 10 vezes.

Exceções: eventos em tempo real (como um leilão), limites essenciais (como uma prova com tempo) e limites maiores que 20 horas.

#### 2.2.2 Pause, Stop, Hide (Nível A)

Conteúdos que se movimentam, piscam, rolam ou atualizam automaticamente precisam oferecer mecanismos para pausar, interromper ou ocultar, quando aplicável, exemplos:

- Permitir pausar carrosséis que avançam automaticamente.
- Oferecer controles para interromper animações.
- Permitir ocultar elementos que se movimentam continuamente.
- Permitir controlar atualizações automáticas de informações.

Quando se aplica:

- Movimento, piscar ou rolagem: quando começa automaticamente, dura mais de 5 segundos e é apresentado junto com outro conteúdo.
- Atualização automática: quando começa automaticamente e é apresentada junto com outro conteúdo. Nesse caso, também vale permitir controlar a frequência das atualizações.

Exceção: quando o movimento é essencial para a atividade.
