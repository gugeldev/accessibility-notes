
O princípio robusto possui uma diretriz:

| Diretriz | Nome       | Objetivo   |
| -------- | ---------- | ---------- |
| 4.1      | Compatible | Compatível |

---
## 4.1 Compatível

Essa diretriz busca garantir que o conteúdo seja compatível com diferentes navegadores, tecnologias assistivas e ferramentas utilizadas pelos usuários.

A ideia é permitir que leitores de tela e outras tecnologias consigam interpretar corretamente os componentes da interface e suas alterações.

Exemplos de acessibilidade nessa diretriz:

- Utilizar elementos HTML semânticos.
- Identificar corretamente botões, campos e outros componentes.
- Informar estados de componentes, como expandido ou recolhido.
- Comunicar mensagens de erro e notificações para leitores de tela.

Exemplo de implementação:

```html
<button
  aria-expanded="false"
  aria-controls="menu"
>
  Abrir menu
</button>

<nav id="menu" hidden>
  <!-- Itens do menu -->
</nav>
```

O atributo `aria-expanded` comunica às tecnologias assistivas se o componente está expandido ou recolhido. Ele precisa ser atualizado via JavaScript sempre que o menu abrir ou fechar.

O critério 4.1.1 Parsing existia nas versões 2.0 e 2.1, mas foi removido na WCAG 2.2, porque navegadores e tecnologias assistivas atuais já lidam bem com HTML malformado.

### Critérios de sucesso

#### 4.1.2 Name, Role, Value (Nível A)

Todos os componentes de interface devem permitir que seu nome, função (_role_), estado e valor sejam identificados programaticamente pelas tecnologias assistivas.

Além disso, alterações nesses atributos devem ser comunicadas corretamente, exemplos:

- Um botão deve ser identificado como botão, não apenas como um elemento genérico.
- Um campo deve possuir um nome acessível.
- Um menu expansível deve comunicar se está aberto ou fechado.
- Um checkbox deve comunicar se está marcado ou desmarcado.

Elementos HTML nativos já atendem ao critério automaticamente. O problema aparece em componentes personalizados:

```html
<!-- Inadequado: o leitor de tela não sabe que é um botão -->
<div onclick="salvar()">Salvar</div>

<!-- Adequado -->
<button type="button" onclick="salvar()">Salvar</button>
```

Sempre que existir um elemento nativo para a função, ele deve ser preferido ao ARIA. Se for realmente necessário usar um `div`, ele precisa de `role`, `tabindex="0"` e suporte a teclado.

#### 4.1.3 Status Messages (Nível AA)

Mensagens de status devem poder ser identificadas programaticamente pelas tecnologias assistivas sem que seja necessário mover o foco até elas, exemplos:

- Informar que um formulário foi enviado com sucesso.
- Comunicar que os resultados de uma busca foram atualizados.
- Avisar que um arquivo começou a ser enviado.
- Informar que uma operação está sendo processada.

Exemplo de implementação:

```html
<div role="status">
  Formulário enviado com sucesso!
</div>
```

O `role="status"` permite que leitores de tela identifiquem a mensagem sem precisar receber foco.

- `role="status"`: anuncia a mensagem sem interromper o que o leitor de tela está lendo. Ideal para sucesso, progresso e resultados.
- `role="alert"`: interrompe e anuncia imediatamente. Deve ser reservado para erros e avisos importantes.

Erro comum: criar o elemento com `role="status"` junto com a mensagem. Muitos leitores de tela só anunciam alterações em um elemento que já existia na página, então o container deve estar presente desde o início, vazio, e o texto ser inserido depois.
